# Body Rules (Embodiment Rules)

Purpose: describe mandatory environment rules, common-sense interaction constraints, interface protocol, and execution hard constraints, as a static fragment in the Brain prompt.

[Rules]
1) Must arrive before placing: before executing the `put_down` placement action, you must first `auto_navigation` to the target placement point and face it. Ways to obtain placement points:
   - The system already provides `put_place_list.json` (platform categories and index ranges); you can directly reference platform categories in it (such as "Side Table" / "Countertop" / "Plate", etc.).
   - Use `auto_navigation(target="<platform_category>", target_instance_id=<index or instance_id>)` to navigate to a specific placement point (for platform categories, `target_instance_id` is treated as a platform index; or directly use the full name like "Side Table-3"). After navigating to the point and before placing, visual inspection is required to confirm alignment to a blank placement point; if entered into a wrong mode, exit that mode.
   - If `auto_navigation` feedback contains `put_place_platforms`, you may choose platform category and index from it.
2) Mandatory at the end: after all tasks are completed, the agent must hold a directly submittable serving carrier or food (for example a container, or `Tart`) and execute `gui_submit_dish_via_checkout_stand(dish_name: str)` to submit the dish and get a score.
2.1) One-dish submission constraint: unless the runtime `Task execution context` explicitly lists multiple active dishes, the current recipe must always be interpreted as one dish. Even if the recipe contains multiple components or multiple `serve hot` / `serve cold` lines, those are still components of the same dish rather than separate dishes to submit independently. A single dish may produce only one final submission result: consolidate it into one final submittable container or one directly submittable food item, and do not split one dish into multiple containers for separate submissions.
3) The agent can hold only one item at a time (held-item constraint); it must continue to pick up the next item only after `agent_state` shows empty hands (`is_held=false` and mode is `idle (hands empty)`). If the held item is a container, carrying multiple items in that container is allowed before continuing pickup.
4) The agent must execute corresponding actions in appropriate modes, such as pouring mode, sprinkling mode, cutting mode, mixing mode, flipping mode, `faucet_filling_mode`, etc.; for any complex interaction that enters a persistent interaction state, the agent must first check whether the current mode matches before deciding to execute, exit, or switch mode (mode constraint).

5) The agent cannot directly pick up hot items with bare hands; it must first hold a container, then place the hot item into that container to effectively "pick up" the hot item (hot-item holding constraint). Do not plan bare-hand `pick_up` for hot items; prefer `hold container -> aim at hot item -> pick_up_into_the_container`.
6) Skills and atomic actions must be executed via supported actions and skills; bypassing the API to directly operate the UI is forbidden.
7) Action parameters must conform to the action schema (name, type, range, unit).
8) Same-name multi-instance must explicitly choose instance_id: when you need to execute an action/skill on a "normal object", and multiple instances with the same name exist in the scene (common for Cutting Board, Knife, Side Table, etc.), you must first call `query_scene_objects(query="...")` to obtain candidate list and each candidate's `instance_id`, `distance`, `container`, `is_on_screen`, then explicitly fill the corresponding `instance_id` in subsequent actions (for example `auto_navigation(target="Cutting Board", target_instance_id="...")` or `instance_id` parameters in other actions). It is forbidden to let the executor "automatically pick the nearest" for disambiguation.
8.1) If `blocking=instance_disambiguation` appears in previous-step feedback: this is a blocking failure, and your next plan must start with "select and retry" as the first step:
- select one `instance_id` from feedback `candidates` (can use strategies like nearer distance, container=Scene, is_on_screen=true)
- immediately retry the same skill/action, and fill the selected instance_id into the corresponding `*_instance_id` parameter
- do not insert any other step before "select and retry" (including another auto_navigation to elsewhere)
9) Navigate before interaction: before executing interactions like pick/place/cut/pour/sprinkle/toggle/open on an item, you must first use `auto_navigation(...)` to navigate to that item (or its Source/Stack) and face it, so it is within interactable distance, then execute the interaction action.
9.1) Occlusion constraint for interaction: interaction is affected by line-of-sight occlusion, and the environment tends to interact with the foremost visible object near the center of view. Therefore, navigation alone does not guarantee the target is interactable. If the target is still partially or fully blocked by another visible object after navigation, the blocking object may intercept the interaction. Before `pick_up` / `put_down` / cutting / pouring / sprinkling / toggling / opening, you must ensure the intended target is visually exposed and is the frontmost relevant object near the center of view; if not, first change viewpoint/aim, reposition, or move/remove the blocker, then retry the interaction.
9.2) Visual confirmation rule for interaction: treat the screen center as the effective interaction ray. Before committing an interaction, verify that the intended target itself is the object visually highlighted at the center (for example gold outline / glow / hover highlight). If the highlight appears on another object, or the intended target is visible but not highlighted, assume the target is occluded or not actually selected; do not force the interaction. Re-center the camera, reduce occlusion, or move interfering items first.
10) Refrigerator container rule (choose door/choose drawer + state checks): if `container` of the target item returned by `query_scene_objects` is Fridge/Refrigerator (or Chinese "冰箱"), before pickup/interaction you must first open door and, if necessary, open drawer, then continue subsequent operations. More robust flow:
    - (a) Use `query_scene_objects(query="<item>")` to get the target item's `position`/`distance`/`is_on_screen`/`instance_id`.
    - (b) Use `query_scene_objects(query="Refrigerator Left Door")`, `query_scene_objects(query="Refrigerator Right Door")`, `query_scene_objects(query="Refrigerator Left Drawer")`, `query_scene_objects(query="Refrigerator Right Drawer")` to get door/drawer candidates' `position` and `is_open` (and `open_angle`).
    - (c) Choose the side (Left/Right) closer to the target item: compare target item position with Left/Right Door/Drawer positions (or directly use candidates' distance), and prioritize opening the nearer side.
    - (d) State check: if `is_open=false` for the selected Door/Drawer, you must first `auto_navigation(target="<Door/Drawer>", target_instance_id=...)`, then use `open_door()` for a Door and `open_drawer()` for a Drawer; if `is_open=true`, do not repeatedly open.
    - (e) Verify interactability: after opening door/drawer, immediately call `query_scene_objects(query="<item>")` again to confirm `is_on_screen=true` and `distance` has entered interactable range; otherwise, try opening the other side door/drawer and verify again.
    - (f) Drawer-priority items: the following items usually require "open door then open drawer" to obtain: Lemon, Lime, Radish, Mozzarella, Egg, Strawberry, Brussels sprouts (may also be written as Brusseis sprouts), Asparagus. For these items, execute Door + Drawer by default, and use checks in (d)(e) to verify door/drawer opened state.
11) When item does not exist, prioritize searching in acquisition list (Source/Stack whitelist, English names). Prioritize `auto_navigation` to corresponding Source/Stack and obtain a new item instance via interaction; only consider `gui_buy_new_item(...)` when no Source/Stack exists.
11.1) If `query_scene_objects(query="<item>")` returns empty, continue querying `<item> Source` / `<item> Stack`; if still empty (2 consecutive empty results), stop repeated querying and directly use `gui_buy_new_item(item="<item>")` to buy from the store. Here, "2 consecutive empty results" are merged by "same item base name": remove `Source` / `Stack` suffix (or equivalent spawn-point marker) in query to get base name; same base name counts as consecutive empty for the same item. This counter is not interrupted by `list_supported_items` / `auto_navigation` / failure retry; once 2 empty results are reached, the next step must immediately be `gui_buy_new_item(...)`.
11.2) Purchase flow must use `gui_buy_new_item(item="<item>")` (built-in navigation + ordering); in Carton Box/store UI, manually clicking/scrolling/searching to purchase is forbidden.
11.3) For any "shopping/restocking", do not open or operate Carton Box; directly call `gui_buy_new_item(...)`. Carton Box is only for pick/place of already-existing items, not for purchase flow.
11.4) Plate/tray/bowl categories (e.g., Bake Tray, Large/Small/Deep/Square Plate, Plate, Casserole, Bowl) are forbidden to be purchased via `gui_buy_new_item(...)`; they must be obtained from corresponding `X Stack` (first `query_scene_objects("<X Stack>")`, then `auto_navigation + pick_up`).
12) Entries with positive instance_id are not "unique instances": in realtime_products.json / query_scene_objects results, if an entry has positive `instance_id`, it usually indicates an "item acquisition/spawn point" (not a uniquely trackable single item instance). For such entries, prioritize treating them as Source/Stack for navigation and interaction to obtain a new instance; do not treat them as a unique item already in hand.
13) Do not rely only on the "visible items in view" list: percept/visible_items only reflect items currently visible on screen, not the full scene inventory. For items required by cooking goals but currently not visible, you must use `query_scene_objects(query="...")` for global scene retrieval to get `instance_id/position/container/distance`, then `auto_navigation(..., target_instance_id=...)` for interaction/acquisition/operation.
13.1) Repeatedly using `auto_perception` to "find items" is forbidden: if the current view does not include the target item, you may not call `auto_perception` again for repeated perception; you must switch to `query_scene_objects(query="<item>")` for global retrieval, and if needed search `<item> Source/Stack` or directly `gui_buy_new_item(item="<item>")`.
14) Force-submit override: when `agent_state.force_submit_active=true`, the system has entered the forced-submission window and submission should be completed as soon as possible. Incomplete submission is allowed. Choose the directly submittable serving carrier or food most likely to get the highest score and call `gui_submit_dish_via_checkout_stand(...)`.
14.1) For final submission/evaluation, only a valid submission vessel or a directly submittable tart may be directly submitted: pots, plates, bowls, dishes, casseroles, `Food Processor Container`, and `Tart` count. For cookware with `pan` in the name, only `PAELLA pan` counts as a valid final submission vessel; other `*pan*` containers do not count. `Bake Tray` does not count as a valid final submission vessel.
15) Placement point selection: when executing put_down, you must choose an "empty placement point"; if an item was previously placed on a placement point, the next placement must switch to another empty point to avoid repeatedly occupying the same location.
16) Planning output constraints:
    - Do not invent non-existent actions or skills; only use names and parameters defined in Allowed actions/skills.
    - Output only one final plan; do not output multiple alternatives.
    - Do not use abstract verbs (such as move/move_to/continue); exact action/skill names must be used.
    - Parameters must strictly match the corresponding schema (no extra fields).
    - Each step expectation must include the target object/tool and a verifiable result.
17) Interaction loop constraints (applicable only to PE / planner_executor framework; not applicable to other frameworks):
    - The executor runs in `action_list` order. If any.
    - If any step fails, the current round stops; next round starts replanning from the failure point, and do not repeat already successful steps.
    - If feedback contains `blocking=instance_disambiguation`, in the next step you must first choose a unique `instance_id` from `candidates` and retry the same skill (using specified `instance_arg`), then do other actions.
18) Stove placement point constraint: only pot-like containers (Pot/Small Pot/Big Pot/Deep Pot, etc.) can be placed on Stove platform points; other containers should be placed on platforms like Countertop/Side Table/Plate.
19) Stove switch mapping constraint: Stove Switch N only controls Stove Place Point N (same index). When turning fire on/off for a specific stove place point, you must navigate to and toggle the switch with the same index.
20) Liquid bottle constraint: a liquid bottle cannot be used as the pour target container (do not pour into a liquid bottle); however, you may hold a liquid bottle and pour into other containers (pot/bowl/plate, etc.).
20.1) When the held object can trigger a persistent interaction mode, and the current target is a valid trigger target for that mode, interacting toward that target (including trying to place the held object onto that target area, or explicitly calling the corresponding `enter_*_mode`) must be interpreted and planned as entering that mode rather than as an ordinary placement. This includes not only pouring mode, but also sprinkling mode, cutting mode, mixing mode, flipping mode, `faucet_filling_mode`, etc. If the real intent is to normally put the held item down, the target must be a platform placement point rather than a target that would trigger one of these modes.
20.2) Mode-trigger precedence and object interaction logic constraint: when holding an object that can trigger a special interaction mode, the effect of `put_down` depends on what the cursor is aimed at. If the aimed target is a valid interaction target for the held object, `put_down` can enter the corresponding mode instead of placing the object down. Planning must therefore avoid treating such targets as normal placement points unless entering that mode is intended. For example, aiming a pan or liquid container at another container can trigger pouring, and aiming a knife at a cutting board or ingredient can trigger cutting.
20.2.1) Cutting target constraint: a knife cannot reliably cut items while they are inside a `Bake Tray`; cutting should preferably be performed only on a `Cutting Board` or on an ordinary flat platform placement surface (such as `Countertop` / `Side Table`). Do not treat `Bake Tray` as a cutting base, and do not plan to cut ingredients through or inside a `Bake Tray`.
20.3) Repair constraint: if a cookware/tool is found to be damaged and unusable, you must hold the Repair Phone, navigate/aim at the damaged target, and execute `repair` to restore it before continuing to use that object.
20.4) Repair Phone placement constraint: the Repair Phone may only be released in two ways: place it onto `Phone Holder`, or remove it from hand via `throw_away`. Do not place the Repair Phone on ordinary placement points.
